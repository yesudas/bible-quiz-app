# Agent guide — Bible Quiz App

## Architecture

- **Public UI**: `index.php` (quiz setup, including questions-per-set, Share Quiz, Embed App, Embed Quiz, and Download PDF), `quiz.php` (sets, progress, review, results summary), `embed.php` / `embed-quiz.php` (bare iframe-embeddable pages — see Embedding below).
- **Data**: `data/{Language}/{bookNo}/*.json` — source of truth for questions. Language folder names may be native-script (`தமிழ்`) or ASCII (`Tamil`).
- **Indexes**: `index/{Language}/` — generated by `i.php` via `includes/index-builder.php`. Do not hand-edit; rebuild after data changes.
- **API**: `api/catalog.php` (GET, per-language books/topics/characters *plus* a `labels` object of translated quiz-type/difficulty text — powers the AJAX language switch), `api/index.php`, `api/questions.php` (POST paths, returns question bodies), `api/share.php` (GET, returns a signed share token for the current selection), `api/leaderboard.php` (GET `?view=top10|all` returns the public leaderboard files; POST records a result — see Leaderboard below), `api/pdf-store.php` (POST a multipart `pdf` file field, returns a `{file}` token) / `api/pdf-download.php` (GET `?file=&name=`, streams it back as `application/pdf`) / `api/pdf-cleanup.php` (POST, no body, sweeps `pdf-temp/`) / `api/pdf-build.php` (POST a quiz selection + header fields, resolves + stamps the matching pre-generated static PDF pair, returns two `{questionsFile, answersFile}` tokens — see the PDF-download-delivery bullet below).
- **Admin**: `a.php` (file browser for `data/`), `i.php`, `sitemap.php` — all require `admin-credentials.php` session.
- **Localization**: `includes/quiz-i18n.php` — quiz type labels, results-summary field labels, and language display names, keyed by language with English fallback. See README's "Languages & localization" section before adding a language. `quizCatalogForLanguage()` reads a language's raw `catalog.json` (books/topics/characters/places with counts) — used both to resolve book display names and to render the homepage's browse-by-book/topic/character/place chip lists.
- **Share links**: `includes/quiz-share.php` — HMAC-signed, base64url short tokens (`payload.signature`) encoding the quiz selection; `share-secret.php` (gitignored, auto-generated) holds the signing key. `quizShareEncode()`/`quizShareDecode()` build the payload positionally — every field after the fixed header (version/lang/type/set-size) is read back in the exact order it was written, so a new field can only be appended at the very end, never inserted mid-structure, or every token field after it decodes wrong. The **"Settings for Competitions"** fieldset on `index.php`'s quiz setup form (`share_expiry`, `share_expiry_unit` — `minutes`/`hours`/`days`, `share_expiry_value`, `share_one_attempt`) is this pattern's most recent addition: `api/share.php` converts whatever unit was chosen into minutes, validates the total is between 5 minutes and 30 days (`1440 * 30`), and computes an absolute `end_time` (`time() + expiryMinutes*60`) — the **end timestamp itself**, not a duration, is what's encoded, specifically so `index.php` only has to compare it against the current `time()` on each visit rather than reconstruct elapsed time. These two fields are appended as a single trailing optional block (1 flags byte — bit 0 = has expiry, bit 1 = one-attempt-only; followed by a 4-byte end-time only when the expiry bit is set) using the same tolerant-read trick already used for the trailing difficulty byte (`if ($offset < $len) { ... }`), so **already-issued tokens from before this feature still decode correctly** (they simply come back with `end_time = null`, `one_attempt = false`) — no `QUIZ_SHARE_VERSION` bump was needed. `index.php`'s `?test=...` handling checks `end_time` against `time()` before honoring a shared link; if expired, it shows an error banner with a nudge link back to `index.php` (carrying the token's own `lang`, per the lang-propagation rule below) instead of redirecting into `quiz.php`. When `one_attempt` is set, `index.php` also sets a cookie — named from a hash of the raw token, expiring at `end_time` — the first time that exact link is used; a later visit with that cookie present is treated the same as an invalid/expired link. This is a soft, cookie-based gate (clearing cookies or using another browser bypasses it) intended for lightweight one-attempt competitions, not a hard security control.
- **Counters**: all site counters live as individual gitignored JSON files under `counters/` (protected from direct web access by `counters/.htaccess` — `Require all denied`), one file per counter so new counters can be added without touching existing ones.
  - **Visitor counter**: `includes/visitor-counter.php` (`quizIncrementVisitorCount()` / `quizReadVisitorCounts()`) reads/writes a single JSON object in `counters/counter.txt` — `{"total": N, "languages": {"English": N, ...}}` — under an exclusive file lock. `counter.php` (included by `index.php`/`quiz.php`/`leaderboard.php`, before those files validate `$_GET['lang']` themselves) does its own lightweight language validation and calls the increment function. `a.php` calls the read-only function to display both numbers; it must never call the increment function (that would count admin visits) — verified with an isolated test (dedicated port, logged requests) that logging into and repeatedly refreshing `a.php` makes zero requests to `index.php`/`quiz.php`/`counter.php` and leaves `counters/counter.txt` untouched.
  - **Share counter**: same pattern, one level simpler — `includes/share-counter.php` (`quizIncrementShareCount()` / `quizReadShareCounts()`) reads/writes `{"total": N}` in `counters/shares.txt` under an exclusive file lock. `counter.php` increments it whenever the request carries a non-empty `?test=...` (a share link), on the same non-bot branch as the visitor increment — this happens before `index.php` decodes/validates the token, so it counts share-link *visits*, not just ones that turn out valid/unexpired. `renderQuizFooter()` (`partials.php`) exposes `$shares2` alongside `$visitors2`, rendered in `footer-links.php` as "Shares: N" next to "Visitors: N".
  - **Embed counter**: same pattern again — `includes/embed-counter.php` (`quizIncrementEmbedCount()` / `quizReadEmbedCounts()`) reads/writes `{"total": N}` in `counters/embeds.txt`. Unlike the share counter (keyed off a query param), `counter.php` keys this off `basename($_SERVER['SCRIPT_NAME'])` being `embed.php` *or* `embed-quiz.php`, since every view of either page is an embed view regardless of its query string — it increments on the same non-bot branch as the other two. `renderQuizFooter()` exposes `$embeds2`, rendered in `footer-links.php` as "Embeds: N" next to "Shares: N". Both pages `include` `counter.php` like any public page, so they also bump the ordinary visitor counter on every view, same as a direct visit to `index.php`/`quiz.php`.
  - **Download counter**: same `{"total": N}` shape in `counters/downloads.txt` via `includes/download-counter.php` (`quizIncrementDownloadCount()` / `quizReadDownloadCounts()`), but a different trigger than the other three — the "Download PDF" button's two files are served as `api/pdf-download.php?file=...` links with no page navigation at the point they're produced, so there's no request for `counter.php` to key an increment off. Instead `assets/js/home.js` POSTs to `api/download.php` (fire-and-forget, `.catch(() => {})`'d, same non-blocking pattern as `api/stats.php`) once `api/pdf-build.php` has resolved and stamped both files — one click, one increment, regardless of the two files it produces. `counter.php` only *reads* `quizReadDownloadCounts()` (unconditionally, not gated on the bot check, since nothing is incremented there) into `$downloads2`; `renderQuizFooter()` exposes it, rendered in `footer-links.php` as "Downloads: N" next to "Embeds: N".
  - A future counter follows the same shape: its own `counters/{name}.txt`, its own `includes/{name}-counter.php` with an `Increment`/`Read` pair under an exclusive file lock — don't add new keys to an existing counter's file for an unrelated metric.
  - **Quiz-activity stats**: `includes/quiz-stats.php` holds three of these counters, all written only from `api/stats.php` (POST, called fire-and-forget by `assets/js/quiz.js`'s `finishSet()` — never blocks or affects the player's own results on failure) — `counters/quizzes-completed.txt` and `counters/questions-answered.txt` (`{"total": N, "languages": {...}}`, one increment per finished *set*, not per whole multi-set attempt) and `counters/questions-by-book.txt` (`{"total": {"<bookNo>": N}, "languages": {Lang: {"<bookNo>": N}}}`). The book breakdown is derived client-side in `getBookCountsForSet()` from each question's `_path` (`"<Language>/<bookNo>/<file>.json"`, same field the mistake-report link uses) rather than from the quiz type, so a topic/character/place set spanning several books still tallies correctly; `api/stats.php` re-validates that the book counts can't sum to more than the set's own `totalQuestions` (tamper-resistance, not a precision guarantee). `counter.php` reads (never increments) all three on every page load and exposes `$quizzesCompletedTotal`, `$questionsAnsweredTotal`, `$topBooks` (top 3 by cross-language total, names resolved via `quizBookNamesForLanguage($counterLang)` — so the *list* of books is language-independent but the *names* match the current page's language), and `$topLanguage` (the language with the highest `questions-answered` total) — `renderQuizFooter()` globals these for `footer-links.php`. Unlike the visitor/share counters, these three are also admin-editable from `a.php?view=stats` (`quizSetQuizzesCompleted()`/`quizSetQuestionsAnswered()`/`quizSetQuestionsByBookForLanguage()`) — an edit there **overwrites** a language's numbers and recomputes the `total` field from scratch, it doesn't add to it, so don't reuse those setters for anything increment-shaped.
- **Mistake reports**: quiz.js shows a "Report Mistake" link per question (`q._path`, added by `api/questions.php`) → `api/report.php` → `includes/mistake-reports.php` appends/dedupes JSON lines in `logs/mistake-reports.log` (gitignored; `logs/.htaccess` blocks web access). `a.php?view=mistakes` lists them, edits the question JSON in place (validated JSON only), and dismisses reports. Editing tags/difficulty there still needs an index rebuild.
- **Leaderboard**: the join/skip popup appears after the *first* set a player finishes, not at the end of the whole quiz attempt — a long book like Genesis split into many 10-question sets may never be finished in one sitting, so waiting for the last set would mean most players never see it. `quiz.js`'s `finishSet()` checks `readAttemptLeaderboardState()` (sessionStorage, keyed by the same `quizAttemptSignature()` used for shuffle-order caching) and only opens the modal (markup in `quiz.php`, behavior in `quiz.js`) when this attempt has no decision recorded yet. Once the player **joins** (both display name and mobile number — mandatory, see below), every later set in the same attempt silently resubmits *that set's own* score with no further prompting; once they **skip**, later sets just redisplay their typed name (if any) with no re-prompt either. **Both display name and mobile number are mandatory to join the leaderboard** — a name-only entry (or Skip) still personalizes the results screen but is never sent to the API and never creates a leaderboard row. `includes/quiz-leaderboard.php` holds all the server-side logic: `quizLeaderboardSubmit()` (called only from `api/leaderboard.php`'s POST handler, which 400s if either field is missing) normalizes + HMAC-matches the mobile number against existing rows and **adds** `correctCount`/`totalQuestions` to that row's running total — the leaderboard score is a *lifetime total* across every set/quiz a phone number has ever finished, not a "best attempt" (deliberately chosen over keep-best, since the same person may play repeatedly and expects every correct answer to count); each submission must be for one finished set only, since passing an attempt-cumulative figure here would double-count it on later sets of the same attempt. There's no `lang` field on a row — a person may play some quizzes in their mother tongue and others in English, so there's no single language to record. The mobile number itself is AES-256-GCM-encrypted for storage in the private master file `logs/leaderboard-data.json` (same protected/gitignored pattern as `logs/mistake-reports.log`). Every write regenerates two public, PII-free files — `leaderboard/top10.json` (top 10) and `leaderboard/all.json` (everyone, descending) — each row just `{displayName, country, score}`. `api/leaderboard.php` (GET) serves those for `leaderboard.php` (public page, "Top 10" + "Show all") and for the "Podium + list" widget on `index.php`'s home page. The AES/HMAC keys auto-generate into gitignored `leaderboard-secret.php` (same pattern as `share-secret.php`/`quizShareSecret()`). `a.php?view=leaderboard` is an admin-only view that decrypts and lists full entries, with both an edit action (`quizLeaderboardEditEntry()` — name/country/score; the mobile number itself is never editable there, since it's the row's identity) and a delete/moderate action — the only place a mobile number is ever decrypted or displayed. `leaderboard.php` and the toolbar link to it (`quiz.php`) both carry `?lang=...` per the lang-propagation rule below (that's only about which language the *page's own labels* render in, unrelated to the removed per-row `lang` field). Country dial codes/names are a single hardcoded list, `quizLeaderboardCountries()` — extend it there, not elsewhere, if a country is missing.
- **Embedding**: two distinct iframe-embeddable entry points, each with its own button on `index.php`'s setup form (`assets/js/home.js`):
  - **Embed App** (`#embedAppBtn`) → `embed.php`, a standalone page (no `renderQuizHeader()`/`renderQuizFooter()`, no menu) that re-renders only the `quiz-setup card-panel` and `leaderboard-widget card-panel` markup from `index.php`, minus the Share Quiz button/reveal (only Start Quiz remains — a signed share token makes no sense for a page meant to be embedded anywhere) and minus the "Settings for Competitions" fieldset (it only ever configured the now-absent Share Quiz link). It ends with a plain "Powered by: Bible Quiz" line linking to `https://wordofgod.in/bible-quiz`. It still `include`s `counter.php` (ordinary visitor-counter bump, plus the embed counter — see Counters below) and `includes/quiz-leaderboard.php` (for the read-only Top 10 widget), and loads the same `assets/js/home.js` as `index.php` — the setup form's language switch, book/chapter/topic/character/place pickers, and catalog chip-list code all already null-guard elements that don't exist on a given page, so dropping the mode-tile/chip-list sections (not requested for embed.php) and the share markup doesn't need any JS changes. The button itself needs no server round trip like Share Quiz does — it just builds `<iframe src="{origin}{basePath}embed.php?lang={current lang}" ...></iframe>` client-side and reveals it in a copyable `<textarea>` (`#embedAppResult`/`#embedAppCodeInput`/`#embedAppCopyBtn`, mirroring `#shareResult`'s markup/CSS) — the visitor picks everything else for themselves once the iframe loads, since `embed.php` has its own full setup form.
  - **Embed Quiz** (`#embedQuizBtn`) → `embed-quiz.php`, which skips the setup form entirely and takes the visitor straight to one pre-configured quiz. Clicking it runs the form through the same `validateSelection()` + `new URLSearchParams(new FormData(form))` pattern Share Quiz uses, then builds `<iframe src="{origin}{basePath}embed-quiz.php?{those params}" ...></iframe>` client-side (`#embedQuizResult`/`#embedQuizCodeInput`/`#embedQuizCopyBtn`) — again no server round trip, since `embed-quiz.php` itself does the validating. `embed-quiz.php` re-parses and re-sanitizes `lang`/`type`/`set_size`/`timed`+`time_unit`+`time_value`/`books[]`(or `book`)/`chapters[]`(or `chapter`)/`topic`/`character`/`place`/`difficulty[]` using the **exact same logic `quiz.php` itself uses** (duplicated, not shared, so keep both in sync if that sanitization ever changes), drops anything it doesn't recognize (e.g. the Settings-for-Competitions fields, which `new FormData(form)` includes but which mean nothing to a quiz page), and 302-redirects to `quiz.php?...&embed=1` — i.e. it's a dumb, stateless forwarder with no HTML of its own, analogous to index.php's `?test=...` token-redirect block but with raw passthrough params instead of a signed token (there's nothing sensitive to protect here — `quiz.php` already accepts arbitrary unsigned GET params directly today).
  - **Embed mode threads through the whole quiz-taking flow, not just the setup page** — `embed.php`'s `<form>` carries a hidden `embed=1` field (and `embed-quiz.php`'s redirect always appends `embed=1`), so landing on `quiz.php?...&embed=1` stays inside the iframe either way. `quiz.php` and `leaderboard.php` each read `$embed = isset($_GET['embed']) && $_GET['embed'] === '1'` and pass `['embed' => $embed]` into both `renderQuizHeader()`/`renderQuizFooter()` (see below) and their own `$homeHref`/`$embedQuery` locals, which redirect "Change quiz"/"Back to home" at `embed.php` instead of `index.php` (even when the visitor arrived via `embed-quiz.php` — there's no "go back to the single pre-configured quiz" page, so it falls back to the full embed setup form) and append `&embed=1` to the leaderboard toolbar link and `leaderboard.php`'s own view-toggle/lang-switch links, so the visitor never breaks out of the iframe into the full site chrome. Forgetting to propagate `embed=1` on any new link added to `quiz.php`/`leaderboard.php` is the most likely way to regress this — grep for `index.php` and `leaderboard.php` link targets in both files as a checklist before adding another one.
  - `renderQuizHeader()`/`renderQuizFooter()` (`partials.php`) both take an `embed` option (default `false`) that skips the `<header>`, PWA install banner, `google-analytics.php` include, manifest/apple-mobile-web-app meta tags, `<footer class="site-footer">` (verse + `footer-links.php` + install button), and `assets/js/app.js` — emitting a bare `<html>/<head>/<body class="...embed-page">/<main class="embed-main container">` shell instead (body also gets `embed-page` appended to whatever `bodyClass` was passed), plus a small `<footer class="embed-footer">` with the same "Powered by: Bible Quiz" line as `embed.php`. This is what lets `quiz.php?embed=1` and `leaderboard.php?embed=1` render chrome-free exactly like `embed.php` itself, instead of only the initial setup screen being chrome-free and then losing that the moment a quiz starts.
- **Download PDF** (`#pdfQuizBtn`, `assets/js/home.js`): a fourth button on `index.php`'s setup form, next to Share Quiz/Embed App/Embed Quiz, for printing the currently-configured quiz instead of taking or embedding it. **As of this rewrite, nothing is generated live** — every possible PDF is pre-generated offline (see the delivery-mechanism bullet below) and the live site's whole job is finding the right pair of static files and stamping the player's own Header/Sub Headers onto them. Clicking the button runs `validateSelection()` (same gate as Share/Embed Quiz) and opens `#pdfModal` (markup in `index.php`, styled with the same `.modal-overlay`/`.modal-box`/`.modal-field` classes the leaderboard join modal in `quiz.php` uses) to collect four optional text fields — Header, Sub Header Details 1/2/3 — each with its own fallback text when left blank (`home.js`'s `pdfForm` submit handler): Header → `"Bible Quiz"`, Sub 1 → `"Organized by: __________________________________________"`, Sub 2 → `"Name: ______________________    Mobile: ______________________"`, Sub 3 → `"Date: _______________     Score: _____ / _____"` — chosen so a quiz printed with no customization still comes out as a usable fill-in-the-blanks worksheet for a competition/group setting, rather than a mostly-blank header area. There's no PDF-size picker anymore — every pre-generated file is fixed at A4. On submit, `pdfAtomicSelection()` (`home.js`) checks the *current setup-form selection* resolves to **exactly one atomic unit** — one of the seven standalone types (`random`/`whole-bible`/`old-testament`/`new-testament`/`kids`/`teens`/`adults`), or exactly one book, one chapter, one topic, one character, or one place (never a multi-book/multi-chapter/difficulty-filtered combination, since those aren't individually pre-generated) — and shows `#pdfFormError` instead of submitting if it doesn't. If it does, `home.js` POSTs `{lang, type, books, chapters, topic, character, place, header, sub1, sub2, sub3}` to `api/pdf-build.php`, which responds `{questionsFile, answersFile}` (two `pdf-temp/` tokens), and the two existing tappable links (`#pdfDownloadLink1`/`#pdfDownloadLink2` inside `#pdfDownloadLinksWrap`) get pointed at `api/pdf-download.php?file=...&name=...` for each — same link-reveal/disable-until-shown pattern this button already used before this rewrite (`pdfDownloadBtn.disabled = linksShown`, re-enabled only on error).
  - **`quiz.js`'s results PDF still rasterizes Tamil/Devanagari/Kannada text client-side, not drawn as jsPDF vector text** (this is the *only* remaining place that happens — the setup-page PDFs below are pre-generated via real browser text shaping instead, see the delivery-mechanism bullet). jsPDF's built-in fonts (helvetica/times/courier) are Latin-only, and these three scripts also need real text shaping (vowel signs/conjuncts get visually repositioned around their base consonant) that jsPDF has no engine for — even embedding a Unicode TTF via `addFont()` wouldn't fix that, the glyphs would still come out in raw code-point order, which is the scrambled look this was built to avoid. `els.downloadPdfBtn`'s "Download results as PDF" click handler calls `await ensureFontsForTexts(collectPdfTexts(stats))` before `buildResultsPdf()`/`buildReviewPdf()` run (`collectPdfTexts()` gathers the heading, player-info line, every quiz-detail row, the encouragement message, and every question's text/chosen-answer/correct-answer/verse-reference/explanation — i.e. everything that could possibly be non-Latin). `detectComplexScriptFont()` tests a string's codepoints against the Tamil/Devanagari/Kannada Unicode blocks; a match gets word-wrapped via `wrapComplexScriptLines()`'s own `canvas.measureText()` (against a matching Noto web font, not jsPDF's metrics) and drawn through `rasterizeLine()` — a real `<canvas>` `fillText()` call, which *does* get correct shaping from the browser's own text layout engine — embedded as a PNG via `pdf.addImage()` at `PDF_RASTER_SCALE`× (2×) the target size for crispness. `quiz.js`'s `makePdfCursor().write()` and the module-level `wrapAnyLines()`/`drawTextLine()` helpers handle both the cursor-driven text and some lines drawn at manual (x, y) positions outside the cursor flow (the banner title inside its colored rect, and the quiz-details card, which has to know its wrapped line count *before* drawing the card background) — `wrapAnyLines()` returns `{scriptFont, lines}` without drawing, `drawTextLine()` draws one already-wrapped line (vector or rasterized) at an explicit position. The explanation line's `italic` styling is dropped (these helpers only distinguish `bold`/`normal`) — explanations render as regular weight text in both languages.
  - **PDF download delivery: pre-generated static files + a live header/footer overlay, not live generation at all.** This replaced an earlier series of fixes (client-side jsPDF generation → a server round trip for Kodular compatibility → a hand-off-to-Chrome trick) after even the most generous version of live generation turned out to be fundamentally unworkable for the largest selections: Tamil "Whole Bible" alone is 788 questions, each needing up to 5 rasterized lines (question + up to 4 options — see the Tamil-rasterization bullet above for *why* those need rasterizing at all), so one "Questions & Options" PDF meant embedding ~4,000 separate base64 PNGs into one in-memory jsPDF document — enough to throw a JS `Invalid string length` error *during generation itself*, before any upload or download was even attempted. No amount of upload-size tuning, batching, or escaping the Kodular WebView fixes that, because the expensive, crashing step is building the document in the browser's own JS engine in the first place. So now: nothing is ever built live. `quiz.js`'s results PDF is unaffected by any of this (still client-side jsPDF, unchanged) — it's already safely bounded (`set_size` caps a set at 100 questions) and can't be pre-generated anyway, since it depends on which answers the player actually chose.
    - **`tools/generate-quiz-pdfs.py`** (local-only — never deployed, never runs as part of a live request) pre-generates a static PDF pair (questions + answer key) for **every atomic selection unit** — each of the 7 standalone types, each book, each chapter, each topic, each character, each place, per language — using the exact same recipe as the sibling `bible-devotions/output_pdf.py` tool: build a self-contained HTML page with the Noto-first font stack, print it to PDF via local headless Chrome's `--print-to-pdf` (real browser text shaping is what renders Tamil/Devanagari/Kannada correctly; no canvas rasterization trickery needed here at all, since this never runs in a constrained in-page JS context). Output lands under `pdf/{Language}/...` (gitignored — large, binary, regenerated locally, uploaded to the server directly, never via git) following a fixed layout: `pdf/{Language}/{type}.pdf`/`-answers.pdf` for the 7 types, `book/{NN}.pdf`, `chapter/{NN}/{CCC}.pdf`, `topic|character|place/{slug}.pdf` (the slug matches `index/{Language}/topic|character|place/{slug}.json`'s own slug — never the raw label, which can be non-ASCII/contain spaces). **Page 1 of every file reserves a blank top-160pt zone** (a plain spacer `<div>` as the first element in `<body>`, not an `@page :first` margin override — that was tried first and found to shift `position: fixed` elements on every later page, since it made the first page's margin differ from every other page's) — nothing is drawn there; the live overlay below can only draw *on top of* existing content, never erase it, so that zone has to start out genuinely empty. Page size is fixed A4 for everything. The answer-key PDF's answer list renders in two CSS columns (`.answers-columns { column-count: 2; }`, each `.answer` row `break-inside: avoid`) to cut its page count roughly in half — the questions+options PDF is deliberately left single-column (its longer wrapped lines don't suit a narrow column).
    - **`includes/pdf-prebuilt.php`**: `quizResolvePrebuiltPaths($lang, $type, $selection)` mirrors `api/index.php`'s own type/book/chapter/topic/character/place normalization (2-digit book keys, `NN-CCC` chapter keys, the same slugs) to find the matching `pdf/{Language}/...` pair, with the same `realpath()`/`str_starts_with()` containment check already used in `api/questions.php`/`api/pdf-download.php`; returns `null` if the selection isn't exactly one atomic unit (e.g. two books checked) or the files don't exist. `quizStampPdfHeaderAndFooters($staticPdfPath, $headerText, $subLines)` uses FPDI to import every page of the static file as a template onto a new FPDF document, sets `SetAutoPageBreak(false)` (critical — FPDF's default ~56.7pt bottom auto-page-break margin otherwise silently triggers on the footer-link `Link()` call near the bottom of each page, inserting a blank extra page per page of input; this is what caused the "many empty pages added" bug), and draws the Header/Sub Headers into page 1's reserved blank zone only. It does **not** redraw a page-number or "WordOfGod.in" footer — the offline generator already bakes both into every page via CSS `@bottom-left`/`@bottom-right` margin boxes, and an earlier version of this function drew its own copy of both on top, which produced visibly doubled/misaligned footer text (FPDF's text metrics don't line up pixel-for-pixel with Chrome's print-to-pdf output). Instead it places an invisible `Link()` annotation over the baked-in "WordOfGod.in" text's approximate position on every page, so the link stays clickable in interactive viewers without drawing anything visible. Needs FPDI+FPDF vendored into `includes/vendor/` (see `includes/vendor/README.md` — a one-time local `composer require` + copy the resulting `vendor/` folder in, since Composer never runs on the server itself, and this environment had no reliable way to fetch that third-party source directly). `quizStampPdfHeaderAndFooters()` throws a catchable `RuntimeException` with a message pointing at that README if the vendor folder isn't populated yet, rather than a bare fatal.
    - **`api/pdf-build.php`** (POST `{lang, type, books, chapters, topic, character, place, header, sub1, sub2, sub3}`): calls `quizResolvePrebuiltPaths()`, 404s with a clear message if it doesn't resolve, otherwise stamps both files and saves each via the existing `quizPdfTempSave()` (same `pdf-temp/` + cleanup machinery `api/pdf-store.php` already uses, untouched), responding `{questionsFile, answersFile}` — two tokens the client turns into the exact same `api/pdf-download.php?file=...&name=...` links the "Download PDF" button already knew how to show.
    - **`home.js`**'s `pdfAtomicSelection()` is the client-side half of the "exactly one atomic unit" rule — it inspects the *current setup-form selection* (not a separate picker) and returns `null` (triggering `#pdfFormError`) unless it resolves to one of the 7 types or exactly one book/chapter/topic/character/place. Multi-book, multi-chapter, and difficulty-filtered selections are deliberately unsupported for this feature (they were never pre-generated) — picking any of those and clicking "Download PDF" just shows the error message telling the player to narrow their selection first.

    - **`quiz.js`'s results PDF** (unaffected by the rewrite above, still client-side jsPDF + a server round trip): builds its file in-page as before, but instead of calling jsPDF's `pdf.save(name)` (which creates a `blob:` object URL and clicks a synthetic `<a>`), it calls `storePdfAndGetDownloadUrl(pdf, downloadName)` — `pdf.output('blob')` POSTed as a standard multipart file upload (`FormData` with a `pdf` field, read server-side via `$_FILES['pdf']`) to `api/pdf-store.php`, not a raw `application/pdf` request body, which some hosts' ModSecurity/WAF rules block outright with a `406 Not Acceptable` before the PHP ever runs (hit in production: the earlier blob-fallback-on-failure design made that failure invisible — no error shown, just a silent revert to the old blob download — until checking the Network tab's `api/pdf-store.php` response surfaced the real 406) — and **returns** (doesn't navigate to) the `api/pdf-download.php?file=...&name=...` URL, which streams the file back with the same header set `files-browser-app`'s proven-working `download.php` uses: `Content-Description: File Transfer`, `Content-Type: application/pdf`, `Content-Disposition: attachment; filename="..."; filename*=UTF-8''...` (both the ASCII and RFC 6266 forms), `Content-Transfer-Encoding: binary`, `Expires: 0`, `Cache-Control: must-revalidate`, `Pragma: public`. This exists because the Kodular Android app embeds the site in a `WebViewer` whose only download-handling logic (`Web_Viewer1.OnDownloadStart` → `ActivityStarter(ACTION_VIEW, DataUri=url)`) can resolve a real `https://` URL but can **never** resolve a `blob:` URL — a plain `window.location.href =` to that URL also doesn't reliably trigger it (Android's WebView download handling appears to need a live user gesture behind the navigation); only a real, user-tapped `<a href>` does (confirmed against `files-browser-app`, a different app on the same WebViewer pattern where downloads already worked that way). So the resolved URL goes on a real anchor (`#downloadPdfLink` inside a `.pdf-download-ready` wrapper, hidden until ready) and the player taps it themselves. If `storePdfAndGetDownloadUrl()` throws, it falls back to the original `pdf.save(downloadName)` rather than losing the download outright. `els.downloadPdfBtn` (labeled `downloadPdf` in `includes/quiz-i18n.php` — `"Generate Results PDF"` for both English and Tamil, deliberately not translated since it's describing an action, not quiz content) stays **disabled** once its link is actually showing (a `linkShown` flag, checked in the handler's `finally`) rather than being unconditionally re-enabled, since there's nothing left to generate until the player starts a new set (which re-renders this whole screen fresh anyway); it's only re-enabled when generation/storage failed, so the player can retry.
    - `includes/pdf-temp-store.php` holds the shared file helpers (`quizPdfTempSave()`, `quizPdfTempResolve()`, `quizPdfTempCleanup()`, `quizPdfTempCleanupBeforeToday()`) behind the protected `pdf-temp/` directory (gitignored, `Require all denied` via its own `.htaccess`, same shape as `counters/`/`logs/`) — filenames are `{timestamp}_{8 hex chars}.pdf`, validated with a strict regex before ever being read back. Two independent, overlapping cleanup sweeps share the same `quizPdfTempDeleteOlderThan(int $cutoffTimestamp)` core: `quizPdfTempCleanup()` (relative, "older than an hour") runs every time `api/pdf-store.php` *or* `api/pdf-build.php` saves something; `quizPdfTempCleanupBeforeToday()` (absolute, "before today's midnight" via `strtotime('today')`) runs via `api/pdf-cleanup.php`, POSTed fire-and-forget from both `home.js`'s `pdfForm` submit handler and `quiz.js`'s `downloadPdfBtn` handler right after each one's own round trip — a coarser backstop so cleanup still happens even on a day where nothing else triggers the hourly one. There's no cron access here, so "on next relevant click" is as scheduled as cleanup gets.
- Every internal link that can be reached while browsing in a non-default language must carry `?lang=...`, or the visit gets silently counted (and re-rendered) as English — `counter.php` and `index.php`'s own `$_GET['lang'] ?? $languages[0]` fallback both default to the alphabetically-first language when it's missing. The header brand logo (`partials.php`, via `renderQuizHeader()`'s `lang` option) and quiz.php's "Back to home" link were missed on this pattern initially and have since been fixed — if you add another link back to `index.php`, pass its language through the same way.

## Conventions

- Keep static assets under `assets/` (css, js, images).
- Shared layout: `partials.php`, `menu-links.php`, `footer-links.php`, `google-analytics.php`, `bot.php` honeypot.
- PWA: `manifest.json`, `sw.js`, icons in `assets/images/`.
- Version cache-bust: `version.php` (`$version`) — appended as `?v=$version` on `assets/css/style.css` and `assets/js/*.js` `<script>`/`<link>` tags on every page. `index.php`/`quiz.php`/`embed.php` also emit it as `window.QUIZ_VERSION` (alongside the existing `window.QUIZ_I18N` inline script, right before the page's own JS bundle loads) so client-side `fetch()` calls can cache-bust the same way: `home.js`'s `loadCatalog()` appends it as `&v=...` on `api/catalog.php` requests and `quiz.js`'s `indexUrl()` appends it on `api/index.php` requests — both endpoints set `Cache-Control: public, max-age=300`, so without a version-keyed param a browser could keep serving a pre-bump response (missing newly-added questions/books) until that 5-minute window lapsed on its own. Bumping `version.php` after a data/index change is what guarantees an immediate fresh fetch instead of waiting out the cache. Both endpoints ignore unrecognized query params, so `v` is inert server-side — it only changes the cache key.
- Public site styling lives in `assets/css/style.css` (Vibrant Playful theme — purple/teal/pink/yellow, Baloo 2 + Nunito). The admin/file-browser tools (`a.php`, `i.php`, `sitemap.php`) use a separate, unrelated `styles.css` at the repo root — don't conflate the two when restyling.
- `assets/js/quiz.js` shuffles each question's `options` (and remaps `correct_option`) the first time it's rendered, flagged via `q.__shuffled`. Any code that reads a question's options/correct answer must go through the same `q` object after `renderQuestion()` has run, not the raw API response, or it'll see the pre-shuffle order.
- Quiz type keys (`quizTypeKeys()` in `includes/quiz-i18n.php`) must stay in their existing order — `includes/quiz-share.php` encodes a quiz type as a 1-based index into that list, so reordering it invalidates every previously issued share link. `place` was appended at the end for this reason when it was added; the next new type must also be appended, never inserted. `quizDifficultyKeys()` (also `includes/quiz-i18n.php`) is encoded as a bitmask by bit position in `includes/quiz-share.php` — same rule: append, don't reorder.
- `topic`, `character`, and `place` are all the same pattern end to end: a tag on the question JSON (`themes`/`characters`/`places`), aggregated into `index/{Language}/{type}/{slug}.json` by `includes/index-builder.php`, listed in `catalog.json`, resolved by `quizIndexLabel($lang, $type, $slug)`, filtered in `api/index.php`, encoded as a length-prefixed string in `includes/quiz-share.php`, and rendered as both a `<select>` (with `data-preselect`) and a chip list (`renderItemLinks()`) in `index.php`/`home.js`. Adding a fourth one of these means touching all of those spots the same way — grep for `character` across the codebase as a checklist. Note `places` in the source JSON is `[{"name": "Egypt", "type": "country"}]` (objects, not bare strings) — `index-builder.php` extracts `name` and currently ignores `type`.
- Difficulty is an orthogonal filter layered on top of any quiz type (`index/{Language}/difficulty/{easy|medium|difficult}.json`, built in `includes/index-builder.php`), applied in `api/index.php` as a path intersection. It threads through `index.php` (form + share-token redirect), `quiz.php` (`data-difficulty`, results summary), and `assets/js/quiz.js` (`state.difficulty`, included in `indexUrl()` and the shuffle-attempt signature).
- The Language `<select>` switch is AJAX-only (`assets/js/home.js`'s `langSelect` change handler calls `loadCatalog()`, no page reload). It re-renders: the `#type` option text and `.type-grid a[data-type-key]` mode tiles (from `catalog.labels.types`), the difficulty `[data-difficulty-label]` spans (from `catalog.labels.difficulties`), `window.QUIZ_I18N.chapterWord`, and the four `#bookLinksList` / `#topicLinksList` / `#characterLinksList` / `#placeLinksList` chip lists (via `renderItemLinks()`) — all from one `api/catalog.php` response. If you add another piece of server-rendered, language-dependent text to `index.php`, it needs a matching update in `loadCatalog()`/`applyLabels()` or it'll go stale after an AJAX language switch (this exact bug — topics staying in English after switching to Tamil — was one root cause fixed here; the other was a genuinely stale `index/` that hadn't been rebuilt after new data was added).
- The same `langSelect` handler also **resets the quiz setup form to its defaults** (type → random, book/chapter checkboxes cleared, difficulty cleared, timer off) and rewrites the URL down to just `?lang=...` before re-fetching the catalog. This is deliberate, not incidental: topic/character selections are slugs from that language's index, so a Tamil topic slug carried into an English `?topic=...` request 404s against `api/index.php` (there's no cross-language mapping). Don't reintroduce "carry the current selection across a language switch" for topic/character/book — reset is the fix, not a preselect/fallback lookup.
- `topicSelect`/`characterSelect`/`placeSelect` support a one-shot `data-preselect` attribute (set from `$_GET['topic']`/`$_GET['character']`/`$_GET['place']` in `index.php`) so clicking a specific topic/character/place chip lands on the setup form with that item already selected. `fillSelect()` in `home.js` applies it once then deletes the attribute — it only fires on the page's initial load, since a language switch resets the form before `loadCatalog()` runs.

## Index builder

`buildQuizIndexes()` writes:

- `catalog.json` — books, topics, characters, places (with counts) for dropdowns and the homepage chip lists
- `types/{random|whole-bible|old-testament|new-testament|kids|teens|adults}.json`
- `book/{NN}.json`, `chapter/{NN-CCC}.json`, `topic/{slug}.json`, `character/{slug}.json`, `place/{slug}.json`, `difficulty/{easy|medium|difficult}.json`

Each index file lists `paths` only; the client splits them into sets using `set_size` from the quiz form (default 10, max 100).

## Security

- Never commit `admin-credentials.php`, `share-secret.php`, `leaderboard-secret.php`, any `counters/*.txt`, or `bot.log`.
- A `counters/counter.txt` from before the per-language upgrade (a bare integer) is migrated into `{"total": N, "languages": {}}` automatically on next write — `quizNormalizeVisitorCounts()` handles both shapes, so don't assume the file is always valid JSON when touching it directly.
- `api/questions.php` resolves paths only inside `data/`. `api/pdf-download.php` applies the same `realpath()`/`str_starts_with()` containment check (via `quizPdfTempResolve()` in `includes/pdf-temp-store.php`) before ever reading a file out of `pdf-temp/`.
- Admin uses CSRF tokens and bcrypt login (see files-browser `a.php` pattern).
- Share tokens (`?test=...`) are verified with `hash_equals()` against a fresh HMAC before being trusted — never decode one without going through `quizShareDecode()`.

## Deploy checklist

1. Copy `admin-credentials.php` on server.
2. Run index build from admin after syncing `data/`.
3. Bump `version.php`'s `$version` after any `data/`/index change (new questions, new book, edited tags) — see the Conventions entry above; skipping this means visitors with a warm cache can keep missing the new content for up to 5 minutes (the `api/catalog.php`/`api/index.php` `max-age`) rather than seeing it immediately.
4. Generate `sitemap.xml` from admin if SEO URLs changed.
5. Ensure the `counters/` directory is writable.
6. Ensure `logs/` and `leaderboard/` are writable (the leaderboard's private master file and its public top10/all JSON files are created on first use).
7. Ensure `pdf-temp/` is writable (both "Download PDF" features write generated PDFs there briefly before the browser fetches them back — see the PDF-download-delivery bullet above).
8. Upload the `pdf/` tree (`tools/generate-quiz-pdfs.py`'s output, run locally — gitignored, not part of a normal deploy) whenever `data/` changes enough to need regenerating it.
9. Make sure `includes/vendor/` actually has FPDI+FPDF in it (see `includes/vendor/README.md`) — without it, `api/pdf-build.php` responds with a clear "not installed" error instead of a PDF, rather than failing silently.
